# Автопостинг @ter_cars через GitHub Actions

Публикации берутся из `api/queue.csv` в публичном репозитории `mashater7/ter-cars`. Время в колонке `datetime_msk` — московское (UTC+3). Строка с пустым `status` ожидает публикации; заполненный статус исключает её из следующих запусков.

## Настройка владельцем репозитория

1. В GitHub откройте **mashater7/ter-cars → Settings → Secrets and variables → Actions → Variables**. Создайте repository variable `AUTOPUBLISH_ENABLED` со значением `false`. До завершения проверок оставьте публикацию выключенной. Без точного значения `true` запланированные публикация и обновление токена не запускаются.
2. На вкладке **Secrets** добавьте repository secrets:

   | Имя | Значение |
   | --- | --- |
   | `ACCESS_TOKEN` | Токен Threads именно аккаунта `@ter_cars`. Перед публикацией скрипт сверяет аккаунт токена. |
   | `THREADS_USERNAME` | `ter_cars` (без `@`). |
   | `GH_PAT` | Fine-grained GitHub personal access token, ограниченный только репозиторием `mashater7/ter-cars`, с разрешением **Repository permissions → Secrets: write**. Используется для записи обновлённого `ACCESS_TOKEN` в repository secret. |

   Вводите токены только в **GitHub Settings → Secrets**. Никогда не коммитьте токены, `.env` с токенами или их значения в файлы, логи и документацию публичного репозитория.
3. Проверьте, что workflow `.github/workflows/autopost.yml` включён в **Actions**, а правила репозитория позволяют workflow сохранять `api/queue.csv` в ветке запуска. Для этой записи workflow использует встроенный `GITHUB_TOKEN` с `contents: write`.
4. Откройте **Actions → Threads autopost → Run workflow**. Ручной запуск (`workflow_dispatch`) выполняет только `python api/autopost.py --dry-run`: показывает подходящие сейчас строки, ничего не публикует и не сохраняет статусы. Изучите лог задания `dry_run`, тексты и время в очереди. Dry run не проверяет действительность токенов и аккаунт через API.
5. После проверки задайте repository variable `AUTOPUBLISH_ENABLED=true`. Это включает последующие запланированные запуски; ручной запуск по-прежнему выполняет только dry run. После первого запланированного запуска проверьте публикации в Threads и сохранённые в репозитории статусы очереди.

## Расписание и очередь

- Публикация проверяется каждые 15 минут: cron `7,22,37,52 * * * *`, то есть на минутах **7, 22, 37 и 52 по UTC** каждого часа. Фактический старт GitHub Actions может задерживаться.
- Обновление токена: cron `0 6 1,15 * *` — 1-го и 15-го числа месяца в 06:00 UTC (09:00 МСК). Задание `refresh` обновляет secret `ACCESS_TOKEN` с помощью `GH_PAT`.
- Текущая очередь заканчивается **2026-11-02**. Для дальнейших публикаций добавьте будущие строки в `api/queue.csv`, сохранив уникальные `id`, CSV-разделитель `;` и существующие статусы.
- Посты, просроченные более чем на шесть часов, получают `skip:опоздал больше чем на 6 часов` и не публикуются задним числом. Заполненные `posted:…`, `error:…` и `skip…` автоматически повторно не отправляются. Не очищайте статус для повтора без проверки фактической публикации.

## Восстановление после сбоя

Если исход публикации неясен или сохранение очереди завершилось сбоем, сначала установите `AUTOPUBLISH_ENABLED=false` и проверьте уже запущенные задания. Это значение отключает будущие запланированные задания, но не отменяет уже работающие. Не перезапускайте публикацию для проверки.

Workflow блокирует новые публикации при обнаружении нерешённого запуска с неуспешным или неопределённым шагом **Publish due posts**, либо с неуспешным сохранением статусов. Разберите каждую такую попытку:

1. **Публикация завершилась ошибкой, была отменена или её исход неизвестен.** Сначала откройте сам аккаунт Threads `@ter_cars` и установите, какие посты действительно появились. Отсутствие записи в логе или статуса в CSV не доказывает отсутствие публикации. До этой проверки не редактируйте очередь и не удаляйте проблемный запуск. Артефакта восстановления может не быть. По проверенным данным восстановите статусы в актуальной очереди, включая `posted:<id>` для уже опубликованных постов; не оставляйте их ожидающими повторной отправки.
2. **Publish due posts завершился успешно, но Commit queue statuses не сохранил очередь.** Скачайте артефакт `threads-queue-recovery-<run_id>-<run_attempt>` из соответствующего запуска; внутри находится `threads-queue-recovery.csv`. Сопоставьте строки по `id` с последней версией `api/queue.csv` и перенесите подтверждённые статусы, сохранив новые строки и правки очереди. Если опубликованный `id` был удалён или переименован, восстановите его с записанным статусом публикации. Проверьте результат по Threads. Если артефакт отсутствует или недоступен, восстановите факты по самому Threads до разрешения сбоя.
3. Проверьте все затронутые строки, закоммитьте исправленные статусы и убедитесь, что коммит находится в ветке, используемой расписанием. Только после этого удалите разрешённый проблемный запуск через **Actions → запуск → Delete workflow run**, чтобы снять блокировку. Сначала скачайте нужный артефакт: удаление запуска удалит и его артефакты.
4. Возобновляйте расписание (`AUTOPUBLISH_ENABLED=true`) только после проверки и коммита всех восстановленных статусов. Проверьте следующий запуск и очередь. Если какие-либо публикации ещё не удалось подтвердить, оставьте автопубликацию выключенной.
